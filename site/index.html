Open Charge Point Protocol for Go

A typed OCPP 1.6, 2.0.1 and 2.1 library for charging backends and charge points.

gocpp is one Go module for both ends of the WebSocket: the CSMS and the charge point. Messages are generated from the official OCA JSON schemas, the wire behaviour follows the specification by default, and one slow or broken charger cannot hold up the others.

Design commitments

What gocpp cares about

Seven commitments shape the library. They are the reason it is built the way it is.

01Typed from the official schemas

Requests, responses and handlers are generated from the OCA JSON schemas for all three versions, so the types cannot drift from the specification.

Read how →

02Spec-correct by default

One outstanding CALL per connection, the error codes and message types of each version. Compatibility with chargers tuned against ocpp-go is an explicit preset, not the default.

Read how →

03One charger cannot hurt the others

Each connection owns its state. A panic, a slow handler or a charger that never answers stays inside its own connection.

Read how →

04Small, measured footprint

One goroutine and about 13 KB per idle connection, with bounds that fail the build when they regress.

Read how →

05Behaviour is tested, not assumed

Differential tests against ocpp-go with a charge-point simulator, conformance suites, fuzzing, chaos tests with real processes.

Read how →

06A path from one process to a fleet

The same handlers run embedded in one server or behind a connection tier, with staged releases. The split mode is marked experimental.

Read how →

07You can see what is on the wire

A frame observer, Prometheus and OpenTelemetry metrics, tracing, and lossy taps that never slow a connection.

Read how →

An OCPP backend is a long-lived connection server for hardware you do not control. Chargers stay in the field for a decade, their firmware interprets the specification loosely, and they reconnect all at once after every deploy. These seven commitments are the consequences we drew from that; each section below states the commitment, why it matters, and the mechanism in the code that keeps it.

Quick start

A CSMS and a charge point in a few lines

Install the module, write typed handlers, and connect a charge point.

  1. Install

    go get github.com/shiv3/gocpp (Go 1.26 or later). Redis, NATS, gRPC and Temporal integrations are separate modules under addons/, so the core dependency tree stays small.

  2. Write typed handlers

    Embed the generated Unimplemented handler and override the messages you care about. Everything else answers NotSupported.

  3. Run both ends

    Start the CSMS, then the charge point. The charge point connects to ws://localhost:8080/ocpp/CP_1 and sends a BootNotification.

package main

import (
    "context"
    "log"
    "time"

    "github.com/shiv3/gocpp/csms"
    v16h "github.com/shiv3/gocpp/v16/handlers"
    v16msg "github.com/shiv3/gocpp/v16/messages"
)

// Embed Unimplemented and override only what you handle;
// every other message answers NotSupported.
type handler struct{ v16h.UnimplementedCSMSHandler }

func (handler) OnBootNotification(ctx context.Context, c *csms.Conn, req v16msg.BootNotificationRequest) (v16msg.BootNotificationResponse, error) {
    log.Printf("boot from %s: %s %s", c.ID(), req.ChargePointVendor, req.ChargePointModel)
    return v16msg.BootNotificationResponse{
        Status:      v16msg.RegistrationStatusAccepted,
        CurrentTime: time.Now(),
        Interval:    300,
    }, nil
}

func (handler) OnHeartbeat(ctx context.Context, c *csms.Conn, req v16msg.HeartbeatRequest) (v16msg.HeartbeatResponse, error) {
    return v16msg.HeartbeatResponse{CurrentTime: time.Now()}, nil
}

func main() {
    srv := csms.NewServer(csms.WithSubProtocols("ocpp1.6"))
    if err := v16h.RegisterCSMS(srv, handler{}); err != nil {
        log.Fatal(err)
    }
    log.Fatal(srv.ListenAndServe(":8080")) // ws://host:8080/ocpp/{cpId}
}
package main

import (
    "context"
    "log"
    "time"

    "github.com/shiv3/gocpp/cp"
    v16client "github.com/shiv3/gocpp/v16/client"
    v16h "github.com/shiv3/gocpp/v16/handlers"
    v16msg "github.com/shiv3/gocpp/v16/messages"
)

// CSMS -> charge point requests this charge point answers.
type handler struct{ v16h.UnimplementedCPHandler }

func (handler) OnReset(ctx context.Context, req v16msg.ResetRequest) (v16msg.ResetResponse, error) {
    return v16msg.ResetResponse{Status: v16msg.ResetResponseStatusAccepted}, nil
}

func main() {
    client := cp.NewClient("CP_1", "ws://localhost:8080/ocpp/CP_1", cp.WithSubProtocols("ocpp1.6"))
    if err := v16h.RegisterCP(client, handler{}); err != nil {
        log.Fatal(err)
    }

    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    if err := client.Connect(ctx); err != nil { // or client.Run(ctx): reconnect with backoff
        log.Fatal(err)
    }
    defer client.Close()

    // One typed method per charge-point-originated message.
    boot, err := v16client.NewCP(client).BootNotification(ctx, v16msg.BootNotificationRequest{
        ChargePointVendor: "Acme", ChargePointModel: "Model-X",
    })
    if err != nil {
        log.Fatal(err)
    }
    log.Printf("boot status: %s, interval: %d", boot.Status, boot.Interval)
}
package main

import (
    "context"
    "log"
    "time"

    "github.com/shiv3/gocpp/core/schema"
    "github.com/shiv3/gocpp/csms"
    "github.com/shiv3/gocpp/v201"
    v201client "github.com/shiv3/gocpp/v201/client"
    v201msg "github.com/shiv3/gocpp/v201/messages"
    v201p "github.com/shiv3/gocpp/v201/profiles"
)

func main() {
    reg := schema.NewRegistry()
    if err := v201.RegisterSchemas(reg); err != nil { // the official 2.0.1 schemas, embedded
        log.Fatal(err)
    }
    srv := csms.NewServer(
        csms.WithSubProtocols("ocpp2.0.1"),
        csms.WithSchemaRegistry(reg),
        csms.WithLenientSchema(), // reject broken messages, repair common field quirks
    )

    // Req and Resp are inferred from the message value: no type assertions.
    err := csms.On(srv, v201p.Heartbeat, func(ctx context.Context, c *csms.Conn, req v201msg.HeartbeatRequest) (v201msg.HeartbeatResponse, error) {
        return v201msg.HeartbeatResponse{CurrentTime: time.Now()}, nil
    })
    if err != nil {
        log.Fatal(err)
    }

    // CSMS -> charge point: a typed call, sent once the charge point is connected.
    go func() {
        time.Sleep(10 * time.Second)
        conn, ok := srv.Get("CP_1")
        if !ok {
            return
        }
        ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
        defer cancel()
        resp, err := v201client.NewCSMS(conn).Reset(ctx, v201msg.ResetRequest{Type: "OnIdle"})
        log.Println(resp.Status, err)
    }()

    log.Fatal(srv.ListenAndServe(":8080"))
}

Each tab is a complete main.go, compiled against the current API; the 1.6 pair was also run end to end. More: examples/csms-minimal, examples/cp-minimal, examples/csms-full, and the usage guide.

Defaults worth knowing. Schema validation is off unless you choose a mode (WithLenientSchema is the one recommended for production). Outbound calls are serialized per connection. Transport keepalive is on: a ping every 54 s and a 60 s read-idle timeout.

Commitment 1

Typed messages, generated from the official schemas

The OCA JSON schemas are the source of truth for 1.6, 2.0.1 and 2.1. Nothing about a message is written by hand.

Why. OCPP 2.1 alone has 91 messages. Hand-written structs drift from the specification one field at a time, and the difference shows up in production as a charger that is rejected or, worse, silently misread.

Generics carry the types

A generated message value such as v16profiles.BootNotification is an ocppj.Message[Req, Resp]. csms.On, csms.Call, cp.On and cp.Call infer both types from it: handlers take a typed request and return a typed response, with no type assertions.

Direction is checked

Every message knows who may send it. Registering a handler or issuing a call in the wrong direction returns ocppj.ErrInvalidDirection; DataTransfer is allowed both ways, as in the specification.

Numbers stay numbers

Every JSON-Schema integer is an int64. Every number is a types.Decimal that is always written as an unquoted JSON number, without relying on process-global settings.

Vendor data survives a round trip

The 2.x CustomDataType keeps properties the schema does not define in Extra and writes them back unchanged. Untyped 2.x properties such as DataTransfer.data are json.RawMessage.

Three API levels are generated for each version, all typed: handler interfaces with one-call registration (v16/handlers), client wrappers with one method per message and an Async variant (v16/client), and free functions (v16/calls). The official schemas are embedded and also used at run time for validation, so the types and the validator can never disagree about what a message looks like.

Mechanism: internal/codegen, schemas/, CI job codegen-drift (make codegen && git diff --exit-code), core/types. See docs/architecture.md.

Commitment 2

Spec-correct by default, compatible on request

The specification decides the default behaviour. Compatibility with existing fleets is an explicit, reversible choice.

Why. A default is what most deployments run. If the default bends the protocol, every fleet inherits the bend and chargers get tuned against it. gocpp makes the specification the default and makes every deviation a named option you can see in your configuration.

Lenient mode: strict about structure, forgiving about quirks

Real firmware gets field formats wrong in a small number of well-known ways. Rejecting those messages loses meter values and transactions; accepting anything hands garbage to your handlers. WithLenientSchema() validates against the official schema, rejects structurally broken messages, and repairs the benign cases before the typed decode, only when the conversion is lossless. Each repair is logged and counted.

Migrating from ocpp-go: a preset, then one switch at a time

This is the path to gocpp's own API. To keep ocpp-go's API and change only the runtime under it, see the drop-in replacement.

Chargers in the field may depend on ocpp-go's exact replies. csms.WithOCPPGoCompat() reproduces the charger-visible behaviour of ocpp-go (its error codes, silent drop of bad message ids, UTC whole-second timestamps, no server pings) so a migration can be two steps: swap the library with the preset on, then turn the individual behaviours back to the specification one at a time. The preset is shorthand for six ordinary options; later options win.

Mechanism: core/dispatcher/callslot.go, core/dispatcher/compat.go, core/schema/lenient.go, core/schema/coerce.go. The full table of differences, row by row with the clause each default follows: docs/migration-from-ocpp-go.md. API mapping: docs/migration-from-lorenzodonini.md.

Commitment 3

One charger cannot hurt the others

Isolation per connection, bounded queues, and failure handling that keeps the process and the rest of the fleet running.

Why. In a fleet of thousands there is always a charger that is muted, flapping, or sending something no one anticipated. The server has to treat that as the normal case: the damage one connection can do must end at that connection.

No global lock on the message path

Reading, dispatching, writing and call tracking use per-connection state only. The one optional shared limit, WithGlobalConcurrencyLimit, is a semaphore you opt into to protect your own backends.

Panics are contained

A handler that panics is recovered and answered with an InternalError CALLERROR. The connection and the process keep running. Panics in observers and async callbacks are recovered too.

Handlers outlive the socket, within a deadline

A handler's context is not cancelled when the charger disconnects, so persisting a StopTransaction can finish. It carries a deadline instead (WithHandlerTimeout, 60 s by default) and a handler can still watch for the disconnect if it wants to.

Bounded queues, backpressure instead of drops

At most 16 handlers run per connection. When they are busy, inbound calls wait in a small queue (4), and when that is full the reader stops reading, which slows that one socket. No inbound call is dropped; a full outbound queue returns ErrQueueFull at once.

An unresponsive charger costs one timeout

The call timeout starts when a call takes the connection's slot, not when it was queued, and a stalled write is aborted by a write watchdog. Senders check the connection context, so a teardown never deadlocks a writer.

Closes say why

1000 for a normal or server-initiated close, 1008 when a newer connection replaced this one, 1009 for an oversized message, 1012 for a drain. Over capacity or while shutting down, upgrades get HTTP 503 with Retry-After before the handshake.

Deploys without a reconnect storm

Restarting a process that holds thousands of sockets makes every charger reconnect at the same moment. Server.Drain refuses new upgrades, then closes sessions at a fixed pace, idle ones first, with close code 1012; sessions with a call in flight get a grace period. WithAcceptRateLimit bounds the handshake rate on the way back in. In a rolling restart of 4,000 simulated chargers, a 60-second drain kept about 96% of the fleet connected throughout and held the reconnect peak at 90 attempts per second, against about 2,000 per second for a plain restart.

Mechanism: core/dispatcher/conn.go, inbound.go, pipeline.go, callslot.go, pending.go; goroutine-leak checks with goleak and the race detector on every CI run. Details: architecture, concurrency bounds, draining (measurement: 4,000 chargers, no TLS, one machine).

Commitment 4

Footprint and latency

One goroutine and about 13 KB per idle connection, and a latency tail that stays short at tens of thousands of messages per second.

Why. A CSMS is mostly idle connections. What a connection costs while nothing happens decides how many chargers fit in a process, and garbage-collector work decides the latency tail when traffic arrives. Both are designed for and both are measured.

One resident goroutine

The reader. Writes happen on the goroutine that produced the frame, under a per-connection FIFO lock. Teardown is a context.AfterFunc; the read watchdog and WebSocket ping are timers.

Small buffers, shared configuration

1 KB read and write buffers per connection instead of the 4 KB default, a configuration shared between connections, and timers armed only when needed.

Allocation work for the tail

Frames are parsed by a scanner that references the read buffer, lenient validation uses a reflection-free decoder, and an optional handler pool keeps warm stacks for high message rates.

What the numbers do and do not say

  • For the same 4,000-charger fleet without CSMS calls, gocpp used 26% less memory than upstream ocpp-go v0.19.0 at 30k messages per second (124 against 167 MB); Heartbeat p99 and server CPU were the same to within a histogram bucket.
  • With lenient validation on, gocpp allocated about 22% more per request than ocpp-go (3.57 against 2.92 KB). With validation off gocpp allocated 1.4 KB, 53% less.
  • In the 25-minute soak (40% mute chargers, 50 CSMS calls per second, five restarts), gocpp did not freeze, crash or leak. Upstream ocpp-go v0.19.0 froze after each of its six starts and served no messages for 69% of the run; it also froze with 5 calls per second, and in a capacity ramp with no calls at all at about 31,700 chargers. Not every setup triggers it: it did not freeze in the 4,000-charger runs without calls.
  • These are single runs on one shared machine over loopback, without TLS. Treat them as orders of magnitude and measure your own workload; the harness and reports are in the repository.

Sizing: what one small server holds

A capacity run limited one embedded gocpp server with cgroups and ramped a quiet fleet against it (Heartbeat every 300 seconds, 20% charging with MeterValues every 60 seconds, 40% mute). On 1 core and 2 GB it held about 93,700 chargers with a Heartbeat p99 at or under 200 ms (about 100,000 with schema validation off), at about 16 KB per connection; upstream ocpp-go v0.19.0 froze at about 26,000 to 31,000 chargers (about 37 KB per connection), before reaching a memory or CPU limit. On 2 cores and 4 GB it held at least 112,000, where the test machine, not the server, ran out of memory. As a sizing rule with headroom: about 60,000 chargers on 1 core / 2 GB and about 100,000 on 2 cores / 4 GB, before TLS. Loopback, single runs. Charts, the reconnect-storm results and the caveats are under Sizing and capacity.

The footprint is guarded in CI

TestIdleFootprintBounds opens 2,000 connections through the real server and fails if heap, stack or goroutines per connection exceed fixed bounds (9 KB heap and 6 KB stack today). The bounds are ratcheted down as the footprint shrinks, so a regression of a few hundred bytes per connection fails the build. TestGatewayIdleFootprintBounds does the same for the connection tier of a split deployment.

Tuning the garbage collector

Above roughly 10k requests per second, a larger GOGC trades memory for a shorter tail. Always set GOMEMLIMIT.

Commitment 5

Behaviour is tested, not assumed

Claims about wire behaviour, failure handling and performance are backed by tests that run in CI.

Why. For a protocol library, "it works with our simulator" is not evidence. The questions that matter are what chargers see on the wire, what happens when a process dies mid-message, and whether last month's performance is still there.

Commitment 6

A path from one process to a fleet

Start with one embedded server. When deploys must not disconnect chargers, split the connection tier from the processing tier without rewriting handlers.

Experimental Gateway mode and everything built on it (the gateway package, csms.NewGatewayServer, WithGatewayLink, Server.Drain, storage.SessionRegistry, the addons link-grpc, link-nats, registry-redis and rollout, the commands gocpp-gateway and gocppctl) is experimental until v1.0: the API may change in minor releases, and each such symbol says so in its doc comment. The embedded csms.Server, the generated packages and the core packages are the stable surface and are unchanged by it.

Why. Deploying a process that owns the sockets disconnects every charger it holds. The code that changes most often is the business logic; the code that must not restart is the connection. Separating the two makes an application deploy invisible to chargers.

The typed API does not change

csms.On, csms.Call, the generated handlers and every schema option mean the same in both modes. Because the backend decides every payload-level error, the CALLERROR on the wire is byte-identical to embedded mode, and a test asserts it.

Epoch-fenced sessions

A session registry assigns an epoch to each connection of a charge point before the upgrade is accepted. Calls carry the epoch and a gateway rejects one that does not match the session it holds, so a delayed write or a stale route cannot reach the wrong connection.

At most once after dispatch

If a backend takes a message and then fails, the charger gets InternalError and the gateway never retries elsewhere. A backend that is draining answers Nack and the message is redispatched within the same deadline.

Callers learn what was delivered

A failed CSMS call reports whether the frame was not sent (safe to retry), sent without a response (the charger may have executed it), or answered.

Staged releases

A backend canary is a routing decision at the gateway. Backends attach with a pool name, and a declarative policy decides which pool serves each charger: by id, by attribute, by OCPP version, or by a stable-hash percentage. No socket is touched, so chargers never notice a step or a rollback. Without a policy only the default pool gets work, so starting a canary changes nothing by itself.

  • Gateway canary. The connection tier has its own procedure: a canary gateway with a soft session cap, filled by a paced partial drain of the others, then rebalanced (gocppctl gateway).
  • Automatic promotion is an optional addon, off by default: addons/rollout steps through a plan, evaluates gates (error ratio, CALLERROR mix, p99 latency) and rolls back in one revision. The documentation recommends operating canaries by hand first.
  • Entry criteria are yours. Backends share your stores, so two versions must read what the other writes. The runbook lists what to check before starting.

In the rollout run (4,000 chargers, 2 gateways, pools of 3 and 2 backends), manual steps of 1%, 10%, 50% and 100% moved 0.9%, 9.4%, 48.7% and 100% of chargers with no disconnects and no charger-visible errors, and each revision reached every gateway in 14 to 140 ms. A canary made to answer 30% of requests with InternalError was rolled back by the automatic controller 20 seconds after its 1% stage was applied.

Running several full CSMS instances behind a load balancer, with calls forwarded to the instance that holds the socket, is also supported (clustering); its message-router API is deprecated in favour of the gateway link.

Commitment 7

You can see what is on the wire

Raw frames, metrics, traces and session events are available without touching the hot path.

Why. When a charger misbehaves, the first question is always "what exactly was on the wire?" The answer should not require a packet capture or a rebuild.

Frame observer

WithFrameObserver receives every inbound frame, including unparsable ones, and every outbound frame after the write attempt: charge point id, version, direction, raw bytes, type, message id, action, time and write error. observability.SlogFrameObserver is a ready-made logger.

Metrics

Prometheus and OpenTelemetry adapters behind one Metrics interface: connections, calls and call duration, pending calls, schema failures and lenient repairs, ping latency, close codes with causes, accepts by result, session duration.

Tracing and message ids

WithTracerProvider emits OpenTelemetry spans. Handlers read the frame's message id from the context, and outbound calls can report the id they were sent with, so application logs join up with the wire.

Frame and session taps

core/observability/tap exports frames and session open/close events to a sink (JSON Lines, NATS, your own) for audit, analytics and replay. It samples, filters and drops under pressure: nothing on the connection ever waits for the sink, and losses are visible as sequence gaps.

Per connection, Conn.Stats() reports when it connected, when it last received and sent, and how many calls are pending or queued. A gateway adds routing, pool and tenant metrics for comparing a canary with stable.

Mechanism: core/observability (frame.go, metrics/prom, metrics/otel, tracer.go, tap). Taps are part of the experimental gateway work. See docs/gateway.md, "Frame and session taps", and docs/performance.md, "What to export".

Already on ocpp-go

Drop-in replacement for ocpp-go

Keep your code and ocpp-go's API; change the server runtime with one line in go.mod.

Why. Rewriting a working backend against a new API is a large step. The compatibility module takes a smaller one: it has the public API of ocpp-go v0.19.0 and serves connections on the gocpp runtime, so an existing application switches with one line in go.mod, usually with no change to its code. The exceptions are a few OCPP 2.0.1 (and 1.6) types corrected to the OCA schemas, such as CompositeSchedule; see the compat README.

One line in go.mod

If your code compiles against ocpp-go v0.19.0, add this line to go.mod, then run go mod tidy and build as before. The import paths in your code stay github.com/lorenzodonini/ocpp-go/....

go.mod, for ocpp-go v0.19.0
replace github.com/lorenzodonini/ocpp-go => github.com/shiv3/gocpp/compat/ocppgo v0.19.0-gocpp.3

Module compat/ocppgo, tag v0.19.0-gocpp.3, built on gocpp v0.4.0. go mod tidy adds gocpp and may raise some golang.org/x versions; the minimum Go version is the module's.

What changes (server side)

  • Each connection is served by gocpp's per-connection dispatcher. There is no dispatcher goroutine or lock shared by all charge points, so a stalled or silent charger does not hold up the others.
  • A panic in an application handler is answered with InternalError; the process keeps running.
  • Close codes are sent as WebSocket close frames; an idle connection is closed with 1000.
  • Outbound requests are ordered per charge point, not globally.
  • New upgrades get HTTP 503 once Stop has begun.
  • One extra package, compat, adds what ocpp-go's API has no place for: admission control, readiness, paced drain, metrics and tracing. Using it is optional.

What stays

  • The public API: import paths, types and signatures are identical. CI runs apidiff against the pinned v0.19.0 tag for all 42 packages and fails on any difference.
  • Payload validation, error codes and error descriptions are ocpp-go's own code.
  • The client side (ws.Client, ocppj.Client, the charge-point types) is ocpp-go's unchanged code.
  • A server that injects its own ServerDispatcher keeps ocpp-go's original code path.
  • A way back without a rebuild: OCPPGO_COMPAT_RUNTIME=legacy selects ocpp-go's original code path everywhere.

How it was checked

  • API. apidiff in CI: 42 of 42 packages identical to ocpp-go v0.19.0.
  • ocpp-go's own tests. ocpp-go's OCPP 1.6 and 2.0.1 test suites run against the module on the gocpp runtime in CI, and pass.
  • Soak. The module held 4,000 simulated chargers for 25 minutes (40% of them not answering server calls, 50 server calls per second, five server restarts) with no stall and no crash: 154 MB maximum RSS, 5,988 goroutines (about 1.5 per connection), Heartbeat p50 / p95 / p99 of 0.3 / 0.6 / 0.9 ms. Upstream ocpp-go v0.19.0 under the same load froze after each of its six starts. In a capacity ramp on 1 core and 2 GB the module held 80,571 chargers at 22 to 23 KB per connection and stopped at a Heartbeat p99 of 1.2 s; upstream stopped at 27,774 chargers (35 to 38 KB per connection) after a freeze.

Read these numbers with care. Single runs over loopback on one shared machine, with a synthetic fleet and no TLS, measured on 2026-11-24 on this module and on upstream ocpp-go v0.19.0 with the same harness. Treat them as an indication and measure with your own traffic before a rollout.

For production, switch in stages: build and run your tests with the replace line, try both runtimes (OCPPGO_COMPAT_RUNTIME=gocpp and =legacy), run a canary, and keep the legacy switch as the fallback. The drop-in keeps ocpp-go's API; to move to gocpp's typed API later, see Migrating from ocpp-go.

Sources: compat/ocppgo/README.md (runtime choice, the compat package, known differences); CI jobs ocppgo-compat and ocppgo-apidiff; the load-test runs of 2026-11-24.

Comparison

gocpp and ocpp-go

A factual comparison for engineers choosing between them, including where ocpp-go is the better choice.

ocpp-go is the established OCPP library for Go, and gocpp owes it a great deal: the conformance suite is ported from its per-message tests, and its behaviour is the reference for the compatibility preset. gocpp's own API is a deliberate rewrite with different trade-offs; the table below compares that API with ocpp-go. Where ocpp-go follows the specification, gocpp does too. If you want to keep ocpp-go's API, the drop-in module above runs it on the gocpp runtime.

The design-level problems of ocpp-go v0.19.0 that can be reproduced with small programs, and what gocpp changes and does not change about each, are written up in docs/ocpp-go-structural-issues.md.

Choose gocpp when

  • you need OCPP 2.1, or all three versions in one module
  • you want generated, typed messages and handlers
  • you run large fleets and care about per-connection cost and isolation
  • you want deploys that do not disconnect chargers (experimental gateway mode)

Stay with ocpp-go when

  • you need a stable v1-style API today; gocpp is pre-v1 (the drop-in module keeps ocpp-go's API and changes the server runtime only)
  • your fleet works and you have no reason to change the wire behaviour
  • you depend on its feature-profile structure or its ecosystem
