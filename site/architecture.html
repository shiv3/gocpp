Architecture

Package layers

Four layers, each depending only on the ones below, with generated code on top and pluggable interfaces on the side.

API layer: csms and cp

The generic On / Call / Send functions, options, the HTTP upgrade with its admission checks, session registration, drain. Version-agnostic.

Engine: core/dispatcher

One Conn per socket: the reader, inbound scheduling, the call slot, pending calls, keepalive timers and teardown. Pipeline is the payload policy (schema, lenient repair, error mapping).

Wire: ocppj, schema, transport

OCPP-J framing and error codes, the JSON-Schema registry and validator, and a small WebSocket interface with an in-memory fake that the tests and benchmarks use.

Heavy integrations (Redis, NATS, gRPC, Temporal) are separate Go modules under addons/, so importing gocpp does not pull them into your dependency tree. The reference commands gocpp-gateway and gocppctl are separate modules too.

Source: docs/architecture.md, the package table in the README.

Architecture

Connection lifecycle

Admission happens on the plain HTTP request; after the upgrade a connection has exactly one path to its end.

Claim before upgrade

With a session registry, the registry assigns the next epoch for the charge point before the WebSocket is accepted, so epoch order follows the order in which sockets were established. A failed upgrade releases the claim.

No handler before OnConnect

Inbound handling is held until the connection is published and the connect callback has returned. A handler can rely on Get(id) finding its connection and on OnConnect having run; frames that arrive meanwhile wait in arrival order.

The HTTP handler returns

Once the reader runs, the upgrade handler returns and releases its goroutine and request. The connection hangs off the server context, not the request.

One way down

Teardown flows from a single cancel(cause). Senders check the connection context before writing and while waiting, so there is no write deadlock and no channel is closed under a sender. The disconnect callback fires once, with the cause.

Source: csms/server.go (serveWS), core/dispatcher/conn.go, docs/clustering.md (claim, epochs, reconcile), docs/draining.md.

Architecture

The one-goroutine connection

A connection is one reader goroutine plus data. Everything else is a timer, a callback, or a goroutine that exists only while a message is handled.

An earlier design used a goroutine for each role: reader, writer, dispatcher, closer, watchdogs. Each one costs a stack and scheduler work even when the connection is idle, and idle is what a charger connection is most of the time. The redesign removed them one by one:

  • No writer goroutine or queue. The goroutine that produced a frame (a handler, a caller) writes it under a per-connection FIFO lock. One lazily armed timer enforces the write timeout and aborts the transport when a write stalls.
  • No dispatcher goroutine. The reader starts a handler goroutine itself when a slot is free, and otherwise parks the frame in the bounded queue that finishing handlers drain.
  • No closer or watchdog goroutines. Teardown is a context.AfterFunc callback; the read-idle watchdog and the WebSocket ping are time.AfterFunc timers.
  • Optional handler pool. At tens of thousands of messages per second, growing the stack of a fresh goroutine per message becomes visible (runtime.copystack was 20% of server CPU samples at 60k messages/s). WithHandlerPool keeps warm workers; it is a hand-off, never a queue, so a slow handler cannot delay another connection. Off by default.

Architecture

Message paths

What happens to a message in each direction, and where each bound and error comes from.

Inbound: a CALL from the charger

  • Parse. A scanner recognises well-formed frames and returns sub-slices of the read buffer instead of copies. Anything else, including every malformed frame, goes to the reflective parser, and a fuzz test checks that both agree on arbitrary input.
  • Routing by type and version. CALLRESULT and CALLERROR resolve a pending call. CALLRESULTERROR and SEND are accepted only on OCPP 2.1 connections. An unknown type is answered with MessageTypeNotSupported on 2.x and left unanswered on 1.6.
  • Scheduling. A CALL takes one of 16 handler slots per connection (and a server-wide slot, if WithGlobalConcurrencyLimit is set). With all slots busy it waits in a queue of 4; with the queue full the reader stops reading. CALLRESULTs keep flowing until that point.
  • Handler context. It keeps the connection's values (charge point id, message id, trace) but is not cancelled by a disconnect; it carries the handler deadline instead. A reply that is ready after the connection is gone is dropped silently.

Outbound: a call from the CSMS

  • One call slot per connection. OCPP-J allows one outstanding CALL per direction. Waiting calls queue per connection, so a charger that never answers delays only calls to itself, by one timeout each.
  • Typed errors. A CALLERROR from the charger is a *ocppj.CallError; timeouts, a closed connection and a full queue are sentinels for errors.Is. Through a gateway or a cluster router the same types come back.
  • Measured overhead. In process, a serialized call costs about 7 microseconds and 55 allocations on one connection, within noise of the unserialized mode (core/dispatcher/call_bench_test.go).

Source: core/ocppj/parse.go, core/dispatcher/inbound.go, pipeline.go, callslot.go, pending.go; docs/usage.md ("Handler context and limits", "Async calls"), docs/performance.md ("Concurrency bounds").

Architecture

The gateway split

Which half of a connection stays at the edge, what crosses the link, and how a session is fenced.

Experimental Gateway mode, its links, the session registry and the tools around them may change in minor releases before v1.0. See the introduction for what is stable.

The seam of the split is dispatcher.Pipeline, the payload policy of a connection. An embedded server runs it inside the connection; in a split deployment the backend runs it. The gateway keeps everything that belongs to the socket (TLS, framing, call correlation, the call slot, timeouts, keepalive, frame observer) and never reads a payload, which is why it rarely needs a deploy and why error codes are byte-identical in both modes.

Handshake with negotiation

The first frame is Hello (protocol range, capabilities, pool, version); HelloAck carries the negotiated protocol and the capability intersection. A disjoint range is rejected loudly, and a frame a peer does not know is answered Unsupported without breaking the stream, so adjacent releases can run mixed.

Epoch fencing

The registry's Claim is atomic and assigns the epoch; Release is a compare-and-delete on it. Every request carries the session epoch, and a gateway rejects a call for a session it no longer holds (ErrSessionStale). Each process keeps a lease, so a crashed one invalidates all of its sessions at once.

Deadlines, not clocks

Deadlines are never compared across hosts. An inbound message carries the gateway's receive time and deadline and the backend uses the difference as the handler budget; a CSMS call carries the time left.

Backpressure and drain

On gRPC, HTTP/2 flow control plus a per-stream in-flight cap is the backpressure. A stopping backend sends Drain, the gateway stops choosing it and acknowledges once its in-flight requests are answered.

Source: docs/gateway.md, docs/design/gateway.md, addons/link-grpc/proto/gocpp/link/v1/link.proto, docs/clustering.md.

RSS is not live memory

Heap plus stack per connection is the live cost: about 12 KB for an embedded server and 11 to 14 KB for a gateway session. The RSS of a process that has just taken 10,000 real clients through a 2-minute connect ramp is about 23 KB per session, for the embedded server and the gateway alike: the difference is garbage from the connect storm that the next collection has not freed and heap spans not yet returned to the system (about 1.7 times live at the default GOGC=100). The 13.6 KB figure was taken with idle connections that sent nothing.

What limits a small server

  • Memory, then the collector, then CPU. On 1 core / 2 GB with lenient validation the Heartbeat p99 went from 57 ms at 93,700 chargers to 1.9 s at 96,000 while CPU stayed under 0.8 core: the heap had reached GOMEMLIMIT and the collector ran continuously. With schema validation off a connection costs less (15.3 against 16.8 KB) and the server got to about 100,000 before p99 crossed 200 ms, now with CPU at the one-core quota.
  • Set GOMEMLIMIT. Without it the same server stopped at 78,000 chargers at 0.24 core, because the heap was allowed to grow to 23.6 KB per connection and hit the cgroup limit. At 80% of the limit the collector works harder and holds 16.8 KB.
  • Two cores and 4 GB were not exhausted. At 112,000 chargers the server used 2.8 GB and 0.33 core with a Heartbeat p99 of 2.4 ms; the ramp ended because the test machine ran out of memory for the load generator. The figure is a lower bound. Memory arithmetic puts the real ceiling at roughly 170,000 to 250,000; that was not measured.
  • A fleet this quiet barely uses the CPU. 90,000 chargers held for five minutes cost 0.27 core on average (Heartbeat p99 at most 51 ms). A five times higher heartbeat rate (every 60 seconds) brought the p99 over 200 ms at 100,000 chargers and the server to a full core at 115,000.
  • Throughput scales with cores. With 5,000 chargers and compressed timers, one core saturated at 47,700 messages per second (p99 100 ms; under 37,000 per second the p99 stayed below 64 ms) and two cores at 97,600 (p99 41 ms). The ocpp-go fork was slightly ahead here, 54,400 and 104,800; gocpp ran with lenient schema validation on and was not measured with it off in this experiment.

TLS changes the arithmetic

The harness speaks plain ws://. A separate micro-benchmark of Go's crypto/tls (TLS 1.3, ECDSA P-256, no client certificates, 20,000 idle connections, one core) measured about 136 us of server CPU per full handshake, or about 7,400 handshakes per second per core, and about 15 KB more memory per idle TLS connection. As an estimate, not a measurement: terminating TLS in the server roughly doubles the memory per connection, so 1 core / 2 GB holds about 50,000 to 60,000 chargers, and reconnecting 90,000 chargers costs about 12 seconds of one core in handshakes alone. Terminating TLS on a proxy or load balancer keeps the numbers above.

Caveats

  • Loopback, no TLS, no network latency or loss; the generator and the server share one machine (separate cores, shared memory bandwidth and cache).
  • Every number is a single run. Throughput varies by 5 to 10% between runs, and the point where a latency criterion trips varies more, because p99 sits near a cliff when the heap is close to GOMEMLIMIT.
  • The two-core figures are lower bounds set by the test machine's memory.
  • The ocpp-go fork (v0.17.2 with fixes) reconnected about every 70 seconds in this harness; its connection and CPU figures may be pessimistic.
  • The servers keep no event history and the handlers are trivial. A server that stores events or talks to a database needs more memory and CPU per message.

Adaptive write linger: CPU against latency

Writes on a link stream are always coalesced: frames queued while a write is in progress leave together, with no timer, so an idle stream adds no latency. The optional write linger goes further: on a busy stream, a frame that would be written alone waits up to d for the frames about to follow. It is adaptive per stream (armed only while frames follow each other at an average interval of at most d/2) and off by default.

  • Below its threshold the linger changes nothing, because it is not armed: about 10,000 frames per second per stream for 200 us, 4,000 for 500 us. With ten backends behind a gateway the same traffic never reaches it.
  • Above it, it trades latency for CPU: roughly 0.6 ms more per round trip at 200 us and 1.8 ms at 500 us, for 12% to 31% less CPU in the fleet measurement and up to half on a single saturated stream. The saving is fewer system calls and thread wake-ups on both ends.
  • The worst case is just above the threshold: 5,000 messages per second on one stream with a 500 us linger took a round trip from 0.13 to 2.5 ms.
  • A fixed delay was measured and dropped: at 260 messages per second a fixed 100 us raised the Heartbeat p50 from 0.8 to 2.1 ms and total CPU by a quarter.

Guidance from the documentation: leave it off unless one gateway-backend stream carries more than about 10,000 messages per second and a millisecond of latency is a fair price for the CPU; then start with 200 us on both ends.

Runtime and tuning guidance

The settings that matter for a server full of long-lived connections, and the defaults that are already right.

KnobRecommendationWhy
GOMAXPROCSLeave unsetGo 1.25 and later follows the cgroup CPU limit. Give the process at least 2 CPUs so GC workers do not time-slice with the reader and handlers.
GOMEMLIMITAlways set, 80 to 90% of the container limitTurns an out-of-memory kill into a more aggressive collection, and is what makes a high GOGC safe. 4,000 connections need about 150 MB at GOGC=100.
GOGC100 below about 10k requests/s; 300 aboveMoves mark phases out of the way of requests; RSS grows roughly in proportion. Never GOGC=off without GOMEMLIMIT; no heap ballast.
Schema modeWithLenientSchema() in productionProtects handlers and repairs firmware quirks. Off is for trusted fleets or a validating proxy in front.
WithOutboundValidation(false)Once handler output is testedRemoves about half of the lenient cost per request.
WithHandlerPoolOff; try 64 workers at high ratesCPU -22% at 30k and -18% at 60k msg/s in the load test; no effect at a few hundred msg/s; larger pools get slower.
WithGlobalConcurrencyLimitSet when handlers hit a shared backendCaps handlers in flight process-wide; excess waits (backpressure), it is not rejected.
WithMaxConnections, WithAcceptRateLimitSet for productionBounds sockets and the handshake rate; refusals are HTTP 503 with Retry-After before the upgrade.
permessage-deflateKeep offCompression with context takeover costs far more per connection than everything else on this page saves.

What to watch

  • go_goroutines per connection: about 1.0 to 1.5. A rising ratio means handlers or calls are piling up.
  • Scheduler latency (/sched/latencies:seconds): a p99 above a few milliseconds means CPU starvation or GC.
  • GC assist CPU: sustained non-zero assist means the allocation rate outruns the collector.
  • Conn.Stats() for per-connection pending and queued calls; gocpp_schema_soft_violations_total for what lenient mode is repairing.

Measure your own handlers before tuning: the numbers on this page use trivial handlers, so they show the library's share of the cost. Run load tests without the race detector and with pprof on.
